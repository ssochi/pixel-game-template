# 里程碑的工作方式

## 一个里程碑长什么样

每个里程碑是 `docs/milestones/Mnn-<slug>.md` 一个文件，包含四段：

1. **目标** — 一句话说清这个里程碑之后，玩家能感觉到什么不同。
   不是"重构 X"，而是"晚上睡觉后能接着上次的存档玩"。
2. **缺陷定位 / 任务清单** — 每条都要有**文件与行号**，或者一条可复现的观察。
   "美术不好看"不是任务；"`roomRug()` 是 5 个同心矩形，48×34 的地毯读成一块色板
   （`src/art/interiors.ts:566`）"才是。
3. **验收标准** — 可以被独立验证的条目。截图能看出来的，或者 `window.game` 能查出来的。
4. **迭代记录** — 每一轮做了什么、验收发现了什么、改了什么。做完了在这里写结案。

## 迭代直到满意

一个里程碑不是"写完代码就完事"。一轮 = 执行 → 验收 → 记录。

验收方式，按顺序：

```bash
npx tsc --noEmit          # 必过
npx vite build            # 必过
```

然后**看画面**。像素游戏的问题在代码里看不出来：

```bash
npx vite --port 5173 --host 127.0.0.1 &
node docs/qa/shot.mjs '[{"name":"farm","warp":[690,650],"time":0.4}]'
```

`window.game` 在 dev 模式下暴露 `warp / setTime / enter / leave / state / farm / inv / useTool / fishing`，
所以任何一个角落、任何一个时刻、任何一个室内都能直接跳过去截图。
素材级别的问题用 8 倍放大页：`/proof.html?g=hero|items|props|town|animals|fish`。

**只有验收过了才算这一轮结束。** 没过就再来一轮，在迭代记录里写清上一轮为什么没过。

## 分工

按 `CLAUDE.md`：

- **规划与验收方**：写任务书、审 diff、跑视觉验收、把关提交。不大规模写代码。
- **执行子代理**：每个任务书限定文件范围，执行完必须过 `npx tsc --noEmit`，不 commit/push。

## 提交纪律

- 每个里程碑至少一个提交，信息写**世界变成了什么样**，不写"修改了若干文件"
- 里程碑结案时，同步更新根目录 `README.md` 的相关章节和"已知的下一步"
- 分支：`claude/2d-pixel-game-assets-c2xoxv`
